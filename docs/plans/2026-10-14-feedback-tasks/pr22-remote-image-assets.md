## User-visible result

Add a single-purpose workflow Fetch image action that accepts a literal/data-bound HTTP(S) URL and returns structured output containing a validated local content hash (plus bounded useful dimensions/format/size metadata). A following existing Update triggering button action binds asset to that output. No renderer/web/device fetches arbitrary remote URLs. A fixture workflow HTTP -> Parse JSON -> Extract avatar URL -> Fetch image -> Update triggering button updates the original button's name/image and keeps the last good display if a later fetch fails.

Put the action in the workflow palette with normal typed binding fields and output metadata, not a one-off custom scripting node. Keep action/config compatibility and validation after expression resolution. Set useful conservative defaults and explicit hard bounds: default downloaded response cap 4 MiB, decoded pixel cap 16,000,000, bounded request/decode time and concurrency. Configuration may lower limits or use a bounded approved range; never accept false/zero to disable safety limits. Document units and maxima. Initial input formats are static PNG, JPEG and WebP only; remote SVG, GIF, animation, video, data/file/blob URLs and filesystem paths are excluded.

## Trusted download, cancellation and privacy

Execute network/decode/ingestion in a trusted host process with a bounded service queue. No arbitrary URL/image-fetch IPC exposed to paired web clients; they may only trigger saved actions under existing paired-deck guards. Validate URL protocol and forbid embedded username/password at every redirect. Bound redirects, stop loops, reject HTTPS-to-HTTP credential downgrade, and apply one deadline across redirects and streaming body/decode. Bound the bytes actually consumed even with missing/lying Content-Length or compressed/chunked responses; cancel readers and close resources on every exit. Reject bad HTTP status with a sanitized bounded reason rather than persisting response bodies or signed URLs.

Never forward credentials/cookies/authorization to a different origin. Public-avatar fetches work without credentials. If an optional bearer token is supported, reuse opaque credentialRef, owner+epoch managed-secret entry/rekeying, immutable in-flight lookup and redaction/protectSecret paths from HTTP; do not accept plaintext credential fields or copy authentication from an earlier API request to the returned avatar host. Cross-origin redirects should drop credentials permanently or be rejected; document/test the policy. Do not print signed URL query strings, headers, raw image bytes or secrets in errors/history/cache metadata. Cache by validated content hash, not secret-bearing URL strings. Existing local/LAN HTTP automation must remain usable; do not expand web access to host networking or add arbitrary file schemes.

Current actions/handlers.ts HTTP requests run in the worker with AbortSignal and bounded text output; they are not a binary image API. Main RPC in runtime/worker.ts already publishes PR21 action begin/end for authority-bound display actions, but rejecting a reply promise alone does not cancel a host fetch/decode. Add focused general main-RPC cancellation where necessary, covering unbound/manual/scheduled calls too, without changing PR20 run launch routing. Use action/request identity and originating worker instance; cancellation, node timeout, worker exit/import/shutdown must abort work or at least prevent its late publication/commit. Do not require display authority merely to fetch a local asset, since an unbound workflow may fetch data; only the later display action may update a button. Keep byte buffers out of graph outputs and large IPC where a hash suffices. Bound native decodes and clean temporary files even if cancellation happens after network success.

## Raster validation and normalization

Use existing sharp/libvips with installed-version-supported APIs. Verify actual bytes/decoder format rather than extension/Content-Type. Inspect bounded dimensions/frame count, then fully decode and normalize to a local static raster before publishing a hash. Metadata alone is insufficient. Reject malformed/truncated pixel data, unsupported formats and animated/multipage PNG/WebP; do not silently choose an animation frame. Honor orientation, strip unnecessary source metadata and choose a documented normalization size/fit compatible with button images (existing uploads normalize to 256x256 PNG). Bound normalized output bytes as well as input bytes and pixels. Preserve image quality and alpha deliberately.

Primary docs checked 15 October 2026: [sharp constructor](https://sharp.pixelplumbing.com/api-constructor/) describes failOn and limitInputPixels, and [input metadata](https://sharp.pixelplumbing.com/api-input/) explicitly reads headers without decoding pixels. Metadata exposes pages/frame information for supported containers. Use options actually supported by the installed sharp version; do not copy newer documented options blindly. Never set unlimited or disable pixel limits. Animation rejection needs explicit format/fixture coverage, including APNG if decoder metadata does not reliably flag it.

Use exclusive temporary files, validated hash filenames and atomic publication. Check lstat/no traversal/symlink substitution where appropriate; generated data cannot overwrite arbitrary paths. Concurrent equal content should converge on one correct hash, not race to partial files. Verify existing content before treating it as a cache hit. Disk failures report failure without losing the prior display or corrupting the workspace. Preserve existing authored uploads/import/export semantics while factoring shared raster ingestion only as needed.
