## Scheduling correctness

Create a testable process-level service with injected clock/timer/launch dependencies, not React timers. Prefer main-owned scheduling and the existing trusted worker run path, with explicit acceptance/settlement acknowledgement so overlap and worker failures do not depend on batched run history. Default to one active run per schedule; skip ticks while active rather than queueing them. Respect the engine's global 64-root cap. Bound timers, retained status and concurrent launches. Distinct schedules may overlap within global limits. A launch failure must clear its busy state and report a bounded reason.

The scheduler should start only once per app process; configure/save/snapshot rerenders cannot create duplicate timers. On clock jumps, system suspend/resume, app restart or runner restart, compute the next future occurrence and never replay accumulated ticks or uncertain side effects. Handle long delays without overflowing native timer limits. Keep timers independent of the editor window and of active deck/page selection. Pause when runner is unavailable; restart only once the worker has accepted the current document. Use epochs/definition snapshots to reject obsolete launch/result callbacks after edit/delete/import/restart. Editing or disabling must remove future ticks; define a deliberate cancel policy for a currently owned schedule run (prefer cancel on disabling/deleting/replacing it) and preserve already committed external effects. Quit cancels timers/owned handles and prevents late launches.

DST policy from the plan is explicit: skip nonexistent local times, and execute a repeated local occurrence once. Do not assume the parser's advertised DST handling equals this policy; verify concrete spring-gap and fall-overlap examples, including a non-one-hour transition such as Australia/Lord_Howe and a non-DST zone. Keep a bounded occurrence identity/watermark if needed across resume/restart to prevent duplicate local occurrences, separate from authored definitions. Do not deduplicate so broadly that a valid later date is skipped. Avoid hand-written timezone arithmetic; use maintained timezone/parser APIs and explicit policy checks.

Research checked on 15 October 2026: [cron-parser README](https://github.com/harrisiirak/cron-parser) documents CronExpressionParser.parse(expression,{currentDate,tz}) and next/take. Its strict mode requires six fields, whereas Decker's UI accepts five; validate five fields first and deliberately adapt (for example a fixed zero seconds field), documenting day-of-month/day-of-week semantics. Do not accidentally accept seconds, empty expressions, aliases or macros through a parser default. [Upstream advisory GHSA-r9w7-75q6-r884](https://github.com/harrisiirak/cron-parser/security/advisories/GHSA-r9w7-75q6-r884) lists versions <=5.10.0 affected and 5.10.1 patched. Verify the current package/API and lock a patched compatible version, plus application-level expression bounds before parsing. If choosing another maintained parser, justify its DST/bounds behavior with primary documentation and tests. Do not vendor a cron implementation.
